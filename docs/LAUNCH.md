# دليل الإطلاق التجريبي — دليل كركوك («كركوك الآن»)

> القاعدة: **لا إعلان عن التطبيق قبل وجود 400 مكان متحقَّق منه على الأقل.** البيانات هي المنتج؛ والمنصة التي تقول «مفتوح الآن» وهي مغلقة تخسر ثقة المستخدم من أول مرة.

## 0) بوابات القرار (Go / No-Go)

| البوابة | الشرط | كيف تتحقق |
|---|---|---|
| **بيانات** | ≥ 400 مكان منشور و≥ 80% منها «تحققنا» خلال 60 يوماً، وكل قسم رئيسي فيه ≥ 15 مكاناً | استعلام 5 و6 في `docs/kpi.sql` |
| **تقني** | كل الفحوصات خضراء + فحص الدخان على النطاق الحقيقي | `npm run test:db && npm test && npm run audit && npm run smoke -- https://النطاق` |
| **أمني** | `audit-security` ناجح، ولا مفاتيح سرية في المستودع، وRLS مفعّل على كل الجداول | `npm run audit` |
| **قانوني** | مراجعة محامٍ لـ `/privacy` و`/terms` و`/content-policy` | موافقة مكتوبة |
| **تشغيلي** | نسخ احتياطي مفعّل وتجربة استعادة، ومراقبة وقت التشغيل، وشخصان يملكان صلاحية مدير | قائمة القسم 3 |
| **تجربة** | بيتا مغلقة 2 أسبوع: لا أخطاء حرجة، و≥ 60% من المختبرين نفّذوا «اتصال/اتجاهات» مرة | استعلام 3 |

## 1) الجدول الزمني

**الأسابيع 1–4 (بالتوازي مع التطوير): جمع البيانات**
- فريق من 2–3 طلاب: كل زيارة = صورة + GPS + ساعات + هاتف عبر `/admin/quick-add` (دقيقتان للمكان). المستهدف ≈ 20 مكاناً لكل شخص يومياً.
- أو تجميع جدول في Excel/Sheets ثم استيراده من `/admin/import` (القالب: `public/templates/places-template.csv`). **المستورد غير موثّق**؛ تُنفَّذ بعده «جولات تحقق» (زر «تحققنا الآن» بعد الاتصال أو الزيارة).
- ترتيب الأولوية: مطاعم، كافيهات، صيدليات، أطباء/عيادات، أماكن أطفال، ثم المولات والمحطات. ابدأ بالأحياء: الواسطي، رحيم آوا، العسكري، المصلى، العصري، شورجة، القورية.
- وقّع أول **30 شريكاً** (باقة «احترافية» مجانية 6 أشهر): فعّلها من `/admin/subscriptions` بمدة 180 يوماً، مقابل عرض حصري وملصق QR.

**الأسبوعان 9–10: بيتا مغلقة**
- 100–200 مستخدم (معارف وطلاب) + مجموعة واتساب للملاحظات. راقب طابور المراجعة يومياً (يجب أن يبقى فارغاً تقريباً).
- كل ملاحظة «المعلومة غلط؟» تُعالج خلال 48 ساعة.

**الأسبوع 11: إطلاق عام**
- الويب (PWA) أولاً. ريلز أسبوعية من القوائم المنسّقة («5 أماكن مفتوحة بعد 12 ليلاً»). ملصقات QR في محلات الشركاء.

## 2) قبل أول مستخدم حقيقي (تقني)

1. **Supabase**: مشروع جديد ← نفّذ `0001…0010` بالترتيب ثم `seed.sql` (للمراجع/الاختبار فقط).
2. **مصادقة**: مزوّد SMS للـ OTP (قرار التكلفة)، Google OAuth، وفي *URL Configuration* ضع النطاق و`/auth/callback`.
3. **Railway**: المتغيرات (`NEXT_PUBLIC_*` قبل أول نشر)، النطاق المخصص، شهادة HTTPS. أضف ترويسة **HSTS** من النطاق/الـ CDN (فحص الدخان يتحقق منها).
4. **أول مدير**: `update public.profiles set role='admin' where id='…'` ثم عيّن مديراً ثانياً (الأخير لا يستطيع حذف حسابه).
5. **قبل تعبئة البيانات الحقيقية**: إن شغّلتَ `seed.sql` للتجربة فنفّذ `supabase/cleanup-demo.sql` (يطلب `set app.confirm_cleanup='yes'` أولاً ويحذف البيانات التجريبية فقط).
6. **حدّث الأسعار** في جدول `plans` إن لزم، وضع `NEXT_PUBLIC_CONTACT_WHATSAPP` لتظهر في `/pricing`.
7. **الاسم والهوية**: تأكد من توفر اسم «كركوك الآن» وحجز النطاق وحسابات السوشال ثم حدّث `appName` في `dictionaries.ts` و`manifest.ts`.

## 3) التشغيل والمراقبة
- **نسخ احتياطي**: Supabase → Database → Backups (يومي، وPITR إن أمكن). جرّب الاستعادة إلى مشروع اختبار مرة قبل الإطلاق.
- **وقت التشغيل**: UptimeRobot (أو مثيله) على `/api/health` كل دقيقة مع تنبيه واتساب/بريد.
- **الأخطاء**: سجلات Railway تحمل أخطاء الخادم كسطر JSON (`"level":"error"`). فعّل تنبيهاً على هذا النص.
- **جدولة** (pg_cron أو Edge Function): `select public.sync_subscriptions();` كل ساعة؛ وحذف القصص المنتهية؛ وتنظيف ملفات المستخدمين المحذوفين.
- **مراجعة يومية** (10 دقائق): `/admin` ← طوابير المراجعة ← بلاغات الليل.
- **جولة تحقق أسبوعية**: `/admin/businesses?filter=stale` (أقدم من 60 يوماً) ← اتصال سريع ← «تحققنا الآن».

## 4) اختبار الأجهزة والشبكة
- أندرويد قديم (Chrome ≥ 90 / Android 8–9)، آيفون Safari، Samsung Internet.
- محاكاة 3G في Chrome DevTools (Fast 3G + CPU ×4): الصفحة الرئيسية ظاهرة < 2 ث.
- جرّب: تثبيت PWA، وضع الطيران (يجب ظهور `/offline` أو نسخة صفحة نشاط زرتها)، RTL في كل صفحة، الوضع الداكن، تكبير الخط 150%.
- كل لغة: `ar` أساس؛ `ku` و`tr` تحتاج مراجعة متحدث أصلي — صدّر الورقة بـ `npm run export:i18n` (ملف `docs/translations-review.csv`).

## 5) أثناء البيتا: ماذا نقيس
شغّل `docs/kpi.sql` أسبوعياً: النشطون، العائدون، إجراءات التواصل لكل 100 مشاهدة، أكثر الأنشطة تواصلاً، نسبة البيانات الحديثة، تغطية الأقسام، المطالبات والاستعداد للدفع.
**هدف 90 يوماً بعد الإطلاق:** 5,000 مستخدم شهرياً، 25% يعودون أسبوعياً، 50 مطالبة بصفحة، 10 أعمال مستعدة للدفع. لا مدينة ثانية قبل تحقق ذلك.

## 6) خطة الطوارئ
- **بيانات خاطئة منتشرة**: أوقف النشاط من `/admin/businesses` (إيقاف) ← صحّح ← فعّل. سجل التدقيق يوضح من غيّر ماذا.
- **سبام/هجوم**: حدود المعدّل في قاعدة البيانات (منشورات، تعليقات، تقييمات، بلاغات…) + حظر المستخدم من `/admin/users`.
- **عطل نشر**: Railway ← Rollback إلى النشر السابق. قاعدة البيانات متوافقة للخلف (migrations إضافية فقط).
- **اختراق مشتبه**: بدّل مفاتيح Supabase (anon/service) ودوّر `SUPABASE_SERVICE_ROLE_KEY`، راجع `audit_log`.

## 7) المخاطر الأساسية
| الخطر | المعالجة |
|---|---|
| بيانات قديمة | تاريخ «آخر تحقق» + زر «المعلومة غلط؟» + جولات أسبوعية + فلتر `stale` |
| تطبيق فارغ | لا إطلاق قبل 400 مكان؛ إخفاء الأقسام الفارغة تلقائياً (العروض/الفعاليات) |
| تقييمات وهمية | تقييم واحد لكل مستخدم + OTP بالهاتف + حدود معدّل + إخفاء من البلاغات |
| الحساسيات المحلية | حياد تام؛ مراجعة بشرية للمحتوى؛ سياسة المحتوى منشورة |
| ضعف الإنترنت | PWA خفيف، صور WebP مضغوطة، عمل جزئي بدون إنترنت |
| تكاليف | خرائط OSM مفتوحة؛ لا AI في الإطلاق؛ مراقبة استهلاك Supabase/SMS أسبوعياً |
